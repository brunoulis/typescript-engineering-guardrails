# PostgreSQL: invariants and operational evidence

Activate for an identified PostgreSQL stack, independently of ORM. Record actual server/driver versions and effective application/migration roles. TypeScript types, Drizzle inference and a successful connection do not prove database integrity, authorization or transaction correctness. See [runnable data contracts](../examples/data/README.md) and [audit worksheet](../templates/data-audit.md).

Model business invariants in the database where possible: primary keys, NOT NULL, UNIQUE, FK and CHECK. Tenant-aware composite references prevent relating one tenant's child to another tenant's parent. Test invalid/null/duplicate/orphan data using the real server; application validation complements constraints. Review nullable UNIQUE semantics and concurrent conflict handling for the actual version. Separate global identifier uniqueness from partition-scoped uniqueness.

Bind query values. Dynamic identifiers require a driver-safe identifier API plus a narrow allowlist appropriate to the operation; value placeholders cannot stand in for table/column names. Select needed columns, bound external range/row/batch inputs and use stable pagination with a unique tie breaker. A full SELECT is legitimate for a deliberately small reference table. Prove N+1 issues by recording actual queries for representative request cardinalities, then verify response parity and reduced query counts after a join/batch change.

For node-postgres, acquire with `pool.connect()`, issue BEGIN, every statement and COMMIT/ROLLBACK through that same client, and release in finally. `pool.query()` distributes work across connections and is not a transaction API. For postgres.js use `sql.begin(async tx => ...)` and only the scoped reserved object. In Drizzle use the transaction callback's object matching the actual adapter. See the [pg contract](https://node-postgres.com/features/transactions) and [versioned postgres.js transaction docs](https://github.com/porsager/postgres/blob/v3.4.7/README.md#transactions). Handle rollback/cleanup failures without silently claiming success.

Choose atomic SQL, locks, uniqueness or isolation for the invariant. Demonstrate concurrent behavior with different connections and a barrier that guarantees both observed the relevant starting state. Avoid sleep-based races. Test the failure after the first mutation to prove rollback, not only an exception before a transaction starts. Cancellation must bound server work and leave the pool usable; tests exercise real `statement_timeout` cancellation. Retries need bounded attempts and an idempotent business contract.

Use a least-privilege application LOGIN, distinct from migrations. For RLS test effective `current_user`, ownership, `rolsuper` and `rolbypassrls`; owners usually bypass and superuser/BYPASSRLS always bypass. Where appropriate FORCE ROW LEVEL SECURITY also subjects owners. Prove both USING visibility/update restrictions and WITH CHECK insert/update restrictions. Transaction-local tenant context must derive from authenticated identity, never an arbitrary client header; deny arbitrary SQL and untrusted ability to alter context. Reuse the same physical pool connection for a different tenant and for no-context requests after both commit and rollback. RLS does not authenticate a user. See [PG17 row security](https://www.postgresql.org/docs/17/ddl-rowsecurity.html).

Size the pool across all replicas, workers and processes against the server connection budget. Bound acquisition, statements, lock waits and idle transactions; close on shutdown. External I/O while holding locks consumes capacity and extends contention. Inspect acquisition wait and active/idle counts, not just query duration.

Use EXPLAIN (ANALYZE, BUFFERS) with representative parameters and data, current statistics and write-cost awareness. Composite/partial indexes should follow predicates/order/selectivity; never mandate an index per table or assert exact plans on tiny fixtures. ANALYZE executes the query, including modifications: use only a dedicated disposable database for executable examples. A transaction rollback does not reverse all external effects. The offline auditor never connects to the target database or runs its SQL. [PostgreSQL EXPLAIN documentation](https://www.postgresql.org/docs/17/using-explain.html).

Migrations need an expand/contract deployment story, old/new client compatibility, bounded backfills, lock/statement timeouts and actual validation. `NOT VALID` plus later validation can separate constraint introduction from scanning where supported; uniqueness/index operations have different constraints. Test upgrade from populated old schema, failure/retry and application compatibility. Describe forward recovery for irreversible drops; a down-file name is not evidence of reversibility. Evaluate concurrent-index transaction restrictions and long locks against the selected server version. The small fixture migration demonstrates compatibility, not production backfill performance.

Static SQL/AST signals remain heuristic. Dynamic SQL, effective privileges, catalogs, transaction paths, query plans and workload costs require explicit runtime/catalog evidence; mark unevaluated rather than inferring security from method names.
