# TimescaleDB: PostgreSQL specialization

Activate only when an extension, migration, dependency or real use identifies TimescaleDB. Begin with [PostgreSQL invariants](postgresql.md), then record server `server_version`, `pg_extension.extversion`, exact driver/ORM versions, image digest, hosting model and enabled feature/license capabilities. No cloud account is an implicit requirement. [Executed self-hosted fixtures](../examples/data/README.md) pin PostgreSQL 17.6 / TimescaleDB 2.22.1 and test actual APIs.

Justify a hypertable through ingestion volume, time-range queries and lifecycle needs. A normal PostgreSQL table may be enough. Choose explicit time type, tenant/device keys, indexes and chunk interval based on observed ranges, ingest rate and active chunk memory. Unique and primary-key constraints must contain **every partition column**, including time and additional space/hash dimensions. This is not global uniqueness of an ID across all times. Use a relational ID registry if that global invariant is required. Test rejected and accepted DDL against the extension, including omission of additional dimensions. [Hypertable uniqueness](https://www.tigerdata.com/docs/build/performance-optimization/hypertables-and-unique-indexes), [2.22.1 DDL API](https://github.com/timescale/timescaledb/blob/2.22.1/sql/ddl_api.sql).

Use timestamptz for absolute instants and define query windows as [start,end). Document bucket origin/alignment/timezone and incomplete end buckets. time_bucket groups observed rows; it does not create absent buckets or turn missing measurements into zero. Calendar buckets in a named zone can span 23 or 25 hours around DST; fixed UTC durations and civil days answer different questions. Tests cover both Madrid changes and a genuinely absent hour. [Time bucket reference](https://www.tigerdata.com/docs/reference/timescaledb/hyperfunctions/time_bucket).

Continuous aggregates need explicit `materialized_only`, refresh windows, watermark/recent-tail behavior, late-arrival budget and monitoring. Real-time aggregation includes recent raw data above the watermark; it does not repair late historical changes below it. Test an initial materialization, a new recent bucket, a late row in an old bucket, stale historical query and explicit refresh repair. Do not rely on a daily scheduler or time passing for correctness tests. Inspect policies independently. [Real-time aggregates](https://www.tigerdata.com/docs/learn/continuous-aggregates/real-time-aggregates), [versioned policy APIs](https://github.com/timescale/timescaledb/blob/2.22.1/sql/policy_api.sql).

Hypercore/columnstore API names and DML support depend on the extension version. For tested 2.22.1 use `timescaledb.enable_columnstore`, `segmentby`/`orderby` and `CALL convert_to_columnstore`, verified on real chunks. Do not paste legacy `compress_chunk` syntax as a universal API. Compare sorted query results before/after conversion and execute the supported insert/update operations afterward. Choose conversion thresholds and segment/order columns with measurements; this fixture establishes fidelity, not storage/throughput gains. [Columnstore procedure](https://www.tigerdata.com/docs/reference/timescaledb/hypercore/convert_to_columnstore).

Design raw/summary retention together with refresh windows, chunk boundaries, bucket width, job lateness and late ingestion. A 30-day raw retention and 7-day refresh lookback can preserve older summaries if manual refreshes also exclude deleted history. A refresh that refetches an old deleted window can remove its summaries. The fixture proves both outcomes with fixed dates, `drop_chunks`, an explicitly nonoverlapping refresh and a dangerous forced deleted-window refresh. It separately adds/inspects policies and immediately disables scheduling. Retention deletes complete chunks, not exact arbitrary row cutoffs. [Retention with aggregates](https://www.tigerdata.com/docs/learn/data-lifecycle/data-retention/data-retention-with-continuous-aggregates).

For fixed-duration windows, first reject raw retention at or below the longest dependent refresh lookback plus an explicit bucket-alignment and scheduler-delay budget. Inspect **every** aggregate over that raw table: a 7-day aggregate does not justify 7-day retention when another aggregate refetches 30 days. Equality offers no margin; chunk deletion rounding is not an operational guarantee. Passing this conservative overlap check alone does not prove safety: verify actual chunk boundaries, refresh alignment, job execution/lateness, late-arrival bounds and manual/backfill refreshes. Calendar durations need actual timezone boundaries rather than fixed millisecond conversion. [Executable configuration example](../examples/data/src/retention-config.ts) and [boundary tests](../examples/data/test/retention-config.test.ts) show a fixed-duration guard, post-normalization validation and verified outcomes; these are application examples, not scanner detection.

Compare desired policy settings with installed catalog state: `if_not_exists` provides creation idempotency, not an update; skipping creation or logging “disabled” does not remove an existing policy. The 2.22.1 fixture proves the old duration persists, then explicitly removes/re-adds a changed retention policy and removes it when disabled, with scheduling paused and catalog assertions. Production reconciliation needs authorization, running-job coordination and a recovery plan; pausing scheduling alone does not prove a running job stopped. Report requested, applied, skipped and failed outcomes separately; swallowed errors or configuration logs cannot establish success. Validate integer settings **after** normalization as well as before it: truncating `0.5` to `0` must not create a zero-day retention policy. Define explicit zero/disabled semantics and reject invalid normalized values. The offline auditor cannot establish installed policy state. [2.22.1 policy APIs](https://github.com/timescale/timescaledb/blob/2.22.1/sql/policy_api.sql).

Verify catalog join semantics against the pinned extension and prove expected objects match in a real fixture. In 2.22.1, the jobs view identifies continuous aggregates through their user view names; joining those names to materialization hypertable names can silently match zero jobs. Reconcile only requested policy fields, preserving job identity and execution controls (pause, future start, timezone, retries and runtime limits); assert both the changed value and retained metadata. Complete requested disables before unrelated DDL can fail. These are behavioral proof obligations, not name-based scanner guarantees. [2.22.1 catalog views](https://github.com/timescale/timescaledb/blob/2.22.1/sql/views.sql), [job APIs](https://github.com/timescale/timescaledb/blob/2.22.1/sql/job_api.sql).

Do not assume materialized aggregates inherit raw-table RLS. Verify support/restrictions for the precise combination before exposing them. The example keeps relational RLS and temporal aggregation separate; the aggregate application LOGIN has SELECT only on a security-barrier view with a fixed tenant and is denied direct raw and aggregate access. This demonstrates that view/role isolation strategy; it does not demonstrate continuous-aggregate-over-RLS support. Never disable protection just to pass tests.

SQL extension operations may remain explicit parameterized SQL alongside Drizzle. Keep batches/row/time windows bounded, define atomicity, cancel server work and close clients. The actual supported matrix is Node+pg full suites, Node+Drizzle hypertable/aggregate smoke, Bun+postgres.js and Deno+npm postgres.js reference suites. Run each real runtime; Node execution is not proof for Bun/Deno. No every-driver/runtime cross-product is required.

Offline analysis inspects recognized literal SQL/options and reports syntax-level heuristics. Dynamic policy windows, catalog state, arbitrary SQL, licensing and workload cost remain unevaluated unless separately inspected. Do not build universal SQL safety claims from regex or names.

When changing this guidance or evaluating an audit agent, use the [retention regression scenarios](retention-regressions.md). Keep the reviewer rubric separate from the agent's task; report observed behavior and missing evidence rather than counting a prose match as successful validation.
